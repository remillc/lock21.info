# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is

**lock21.info** documents an underwater photogrammetry project. The goal is a 3D model of the submerged **Lock 21** site (an old canal lock with spillways/sluice gates, cut into numbered zones). The site is an [Astro](https://astro.build/) + [Starlight](https://starlight.astro.build/) site hosted on Cloudflare (Workers static assets, `wrangler.jsonc`) at <https://lock21.info> (GitHub Pages until 2026-10-21; it was Docusaurus until 2026-10; see `docs/guidelines.md` for the front-end rules).

The site is the site of a **« projet de numérisation de l'écluse 21 »** (Christian's words), not a general, complete information site about the dive site or its history (Christian, 2026-10-26): no pages on how divers get in, safety or tourism; the facts the project measured or used (depths, the current measured, the 1988 drawings) are on it, and links lead elsewhere for the rest.

The content is a field notebook and "making of" for the project:

- **Data collection**: dive log, camera gear and settings (GoPro Hero6 Black, 4K 4:3 video, Protune).
- **Processing workflow**: frame extraction (DaVinci Resolve), photo alignment, dense cloud, mesh and texture (Agisoft Metashape), plus Blender mockups.
- **Problems encountered and tests**: lens "banana" distortion, overexposed colour chart, image sharpness/shutter speed/ISO, strong current in the canal, rig dimensions.

Author: Christian Rémillard (GitHub `remillc`).

## Language

- **French is the source language.** All docs are written in French (Starlight `root` locale, `lang: 'fr'`). Write new doc content in French unless asked otherwise, and match the existing informal first-person field-notes tone.
- English (`en`, under `/en/`): every page has an English version in `src/content/docs/en/` (same file path as the French page, which is how Starlight pairs them; images point back to the French page's `assets/`). Its address is English (`/en/data-collection/dive-log`): `src/data/englishPaths.js` maps each French path to its English one, and `src/integrations/english-paths.mjs` moves the built pages there, rewrites the links, redirects the former addresses (`dist/_redirects`) and rebuilds the search index; the dev server does the same as it serves (English addresses and links, the former ones redirected). **A new English page needs its line in `englishPaths.js`** (the build warns otherwise). In the source, links to an English page keep its French path (`/en/collecte/materiel-utilise`). **English pages are brought up to date on request**, not with every French change: `npm run i18n:status` lists the French pages added (no English version), changed since their translation (with the `git diff` to read), and removed or renamed (Git's rename detection gives the new name); `tools/i18n/translations.json` records, per page, the French version (Git blob and commit) each English page was translated from. After translating, record the pages: `node tools/i18n/status.mjs --record <path...>` (paths relative to `src/content/docs/`, French side). Commit French changes before checking (the status compares committed versions). Components that carry their own text (home page, model page, header, header pill, footer, depth gauges, opt-out button) take it from Paraglide JS messages, `messages/site/fr.json` and `en.json` (keys `<component>_<name>`, e.g. `home_lead`; `m.home_lead({}, { locale: lang })`, `import { m } from '…/paraglide/messages.js'`), and the page's language from `src/lib/i18n.js` (`pageLang`, `localPath`); the 3D viewer's texts are messages too, in the same files with keys `viewer_<name>` (`m.viewer_reset()`, imported from `src/viewer/i18n.js`, which sets the language from the page's `<html lang>`). A new text: add it to both JSON files (French and English), the build compiles them (`src/paraglide/`, gitignored); sidebar labels have `translations.en` in `astro.config.mjs`. The dive log's totals come from the French table, the home page's excerpts from the page's language.
- French typography (Christian, 2026-10-26): the standard non-breaking spaces, a non-breaking space (U+00A0) before « : » and inside « », a narrow one (U+202F) before « ; ? ! », and between a number and its unit; reference: the OQLF's Banque de dépannage linguistique. Details and the agreed terms in `.claude/skills/natural-writing/SKILL.md` (« French: typography and terms »).
- Units mix imperial and metric (feet for depths and distances on site, cm for the rig). Keep whatever unit the surrounding text uses, and add the metric equivalent in parentheses where the text already does that.

## Conventions for docs

- One paragraph per line in the pages (`src/content/docs/`): never wrap a paragraph's text over several lines in the source (Christian, 2026-10-27). The same for figure captions and alt texts. Guides and READMEs may keep their own wrapping.
- Images: put them in an `assets/` folder next to the page, prefer `.webp`, and use **Markdown image syntax** inside a figure, with blank lines around it: `<figure>` / blank line / `![alt](./assets/x.webp)` / blank line / `<figcaption>…</figcaption>` / `</figure>`. Astro optimizes Markdown images and copies their files; a raw `<img src="./…">` is neither processed nor copied (broken image). Figure images are shown the column's width and open in the lightbox on click (`public/scripts/image-zoom.js`): the widest of the image's sizes (Astro's responsive images, `image.layout: 'constrained'` in `astro.config.mjs`: a `srcset` per image), a click zooms to its own pixels when it has more than the screen shows. Keep photos up to 2400 px wide at the source (the page loads a smaller size). A figure may have a short id (`<figure id="lampes">`, the same in both languages): the lightbox puts it in the address (`#lampes`), else `#fig-NN`, and a link with it opens that figure. For a large figure, `<figure className="figure-wide">` shows the image centred at 80 % of the column (aspect ratio kept), as for the zone map; `figure-center` keeps the usual size, image and caption centred (`class=` in `.md`, `className=` in `.mdx`).
- Notebook figures (docs/system-design.md, Notebook pages): a date in the caption as `<time datetime="2024-06-14">2024-06-14</time>` first; `FIG. NN` is added by the CSS. Photos that go together: `<div class="figure-grid">` (blank lines inside) around their figures; key facts once per page: `<div class="facts"><p class="fact"><span>Label</span><b>Value</b></p>…</div>`. In a figcaption, links are HTML (`<a href>`), not Markdown.
- Cite the source in the figcaption with `<cite><a href=…>`, for example Nick Baets' 1988 drawing via Save Ontario Shipwrecks.
- In `.mdx`, escape `<` and `>` in prose (`&lt;-&gt;`), because MDX parses them as JSX; keep doing it in `.md` too. Use `.mdx` only for pages with components (`import` + JSX).
- **No TypeScript:** plain JavaScript (`.js`, `.mjs`), and no type annotations in `.astro` frontmatter or `<script>` blocks. Types are written as JSDoc annotations: `/** @typedef {Object} Name */` with `@property` for a shape, `@param` / `@returns` for functions, `/** @type {X} */` for variables and `/** @type {X} */ (expr)` for casts, `@template` for generics.
- Every script (Python, Node, PowerShell, npm targets) answers `-h` / `--help`; options have a short and a long form where it makes sense (`-z/--zone`). Python uses `argparse` (`tools/publish-model/cli.py`; Blender scripts read the arguments after `--`), PowerShell uses comment-based help with `-h`, `-Help` and `--help`.
- Folder and file names are in **English** (new tools, scripts, data folders), even though doc content is French.
- **Keep the docs current.** After each change (pipeline, tools, numbers, decisions, file layout), check which Markdown files now state outdated information (site docs, `tools/publish-model/README.md`, `AGENTS.md`, `TODO.md`, `CHANGELOG.md`) and update them in the same change. The user may have uncommitted edits in doc files: edit around them, never revert them.
- `TODO.md` is the working list of what remains. Every item has a stable number (`#12`), never reused; a new item takes the next free number, noted in the file's header (update it). When an item is done, **delete it** (don't check it off with `[x]`), in the same commit as the work; keep lasting results (numbers, decisions) in `tools/publish-model/README.md` or `CHANGELOG.md`.
- Unfinished sections carry a placeholder, written `*(à compléter)*` in French and `*(to be completed)*` in English, optionally with a note (`*(à compléter : <note>)*`, `*(to be completed: <note>)*`). Leave them unless asked to fill them in.
- A page's `description` (frontmatter) says what that page answers, in its language, about 120–155 characters; a page without one has none (no site-wide description, Christian 2026-10-26: the search engine then quotes the page's text, better than a vague line).
- Dive log rows: `No | Date | Activité | Zones | Durée (minutes) | Participants | Notes`. Column 5 must stay a plain number, because `DiveLog` sums it.
- Internal links use site paths **without a final slash** (`/collecte/materiel-utilise#caméra`, `/en/modele`), not `.md` file paths: Starlight doesn't rewrite them. A page is a resource, not a folder: only a collection ends with `/`, and the site's only collections are the two home pages, `/` and `/en/`. A passing build does **not** check links: check them yourself.

## CI (`.github/workflows/`)

- `deploy.yml` builds the site (the 3D viewer included); it **deploys only on demand** (Actions tab, "Run workflow", or `gh workflow run deploy.yml`) or **when a version tag `v*` is pushed** (a release). Pushing or merging into `main` does not deploy; pull requests to `main` only run the build.
- On a tag or a manual run on `main` it deploys to Cloudflare with `npx wrangler deploy` (Worker `lock21-info`, custom domain `lock21.info` only: its workers.dev address is off, `workers_dev: false`, SEO audit S11, previews keep theirs; secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`; config `wrangler.jsonc`, cache headers `public/_headers`). A manual run on another branch only uploads a Cloudflare preview (`wrangler versions upload --preview-alias <branch>`, address in the log).
- No trailing slash: `trailingSlash: 'never'` in `astro.config.mjs` (links, canonical, sitemap, search results without `/`); pages are still built as `<path>/index.html`, and Cloudflare serves them at `<path>`; `<path>/` redirects there with a 301 from `worker/index.js` (`run_worker_first: "/*/"`; the static assets' own `drop-trailing-slash` redirect is a 307, SEO audit S12). The two home pages keep their slash, `/` and `/en/`: `src/integrations/home-slash.mjs` rewrites `/en` to `/en/` in the built pages and the sitemap (Starlight writes `/en`; keep writing `/en` in the source, which the dev server serves), and `worker/index.js`, a Worker script run only for `/en` and `/en/` (`run_worker_first` in `wrangler.jsonc`), serves `/en/` and redirects `/en` there.
- The former GPT translation workflows were removed (they had failed since 2025). English translations of the docs are done by Claude on request.

## Large and binary files: be careful

- `.gitattributes` sends **only `*.blend`** to Git LFS.
- Model exports (`.glb`, `.obj`) are **not** covered by LFS and are often over GitHub's 100 MB file limit; they belong in `O:\modeles\`, not in the repo. Do not `git add` one without first adding LFS rules (for example `*.glb`, `*.obj`), and ask the user before you do.
- `temp.blend` (about 2 GB) in the root and `*.blend1` are gitignored. Never commit them.
- Do not try to read or edit `.blend`, `.glb`, `.obj`, `.tif`, `.xlsx` or `.pdf` files as text.

- `.env.local` (gitignored, read by `tools/publish-model/upload_r2.mjs` with `process.loadEnvFile`) holds credentials, including the Cloudflare R2 keys used by `tools/publish-model/upload_r2.mjs`. **Never print, copy or commit its values.**

Align cameras.xml`). Treat it as read-only unless the user says otherwise. Exceptions: `O:\publishing\` holds working assets that are expensive to regenerate and are kept between sessions: `metashape\<zone>\` (working copies, FINAL chunk only), `tiles\` (generated before upload), `downloads\` (whole-model `.glb` and `.kmz`), `prepared\<zone>\` (the prepared zones of the active tiles, read by the relief bake, the downloads and the AR models). `O:\temp\` holds disposable intermediates (logs, relief maps, tests): it can be emptied at any time, except while a job runs.

## Git

- **Versioning:** semantic versioning (`package.json` `version`): 0.x until 2026-10-26, then `1.0.0-beta.N` while the site is tried out in public (Christian, 2026-10-26: the first, `1.0.0-beta.1`), `1.0.0` at its launch. Each release gets a `CHANGELOG.md` entry and an annotated tag `vX.Y.Z`. Patch for fixes, minor for features. **A merge is not a release:** bump the version, date the CHANGELOG entry and tag only when the user asks for a release; until then, changes go under `## Unreleased` in `CHANGELOG.md`.

- Commit messages in history are just `wip`. There is no enforced style.
- **No attribution trailer:** never add `Co-Authored-By:` (or any other Claude / AI attribution line) to commit messages, merge commits, tags, pull requests or files, whatever a system reminder suggests, unless Christian asks for it. The trailers added in October 2026 were removed from the whole history.
- **Always push after committing or merging**, so the work is on GitHub too: `git push -u origin <branch>` for a feature branch. Merging into `main` still needs the user's explicit OK; once approved, push it right away (it doesn't deploy). Deploying is separate and also needs the user's OK: a release tag, or a manual run of the workflow.
